# 初始化workflow：建立项目文档，对齐方向，写总计划

使用场景：新建的项目，或者第一次使用 ata 的已有项目；以及 STATUS 当前主线为「初始化」，即上次初始化还没做完。已经在用 ata、只是缺少某份文档的项目不走本流程，按 master.md 第 4 节补建。

上次初始化没做完时，按 STATUS 写的进度从对应的步骤接着做。

## 工作流程

### 1. 判断起点

用目录列表和 `git log --oneline -5` 判断，不通读：

- **新建项目**：目录是空的，或者只有 README、LICENSE 这类初始文件。目录还不是 Git 仓库时，和用户确认后执行 `git init`。
- **已有项目**：已经有代码或文档，第 3 步要先摸底。

完成标准：你明白当前项目是处于新建状态还是已经有了一定的规模。

### 2. 建立文档骨架

按 `references/docs.md`「标准文档」，把所有标准文档一次建好，先只写骨架，后面各步再往里填。这样每类信息从一开始就有自己的位置，不会因为该放的文档还不存在，就写进别的文档。

- `docs/STATUS.md`：按 `references/docs/status.md` 的模板建，当前主线第一行写 `初始化`，第二行写当前进度。
- `docs/decisions.md`：按 `references/docs/decisions.md` 的模板，只建标题和说明。
- `docs/scratchpad.md`：按 `references/docs/scratchpad.md` 的模板建。
- `docs/PROJECT_PLAN.md`：只写各节标题，内容在第 5 步写。
- `AGENTS.md`：按 `references/docs/agents-md.md` 的模板建，项目定位暂时留空；会用到 Claude Code 时，同时建 `CLAUDE.md`。
- `docs/ata/` 下的两份实践手册和收件箱：按 `references/docs/practices.md` 的模板建。
- 已有项目：已经存在的文件不覆盖，只补缺的部分；同名文件用途不同时，问用户怎么处理。

建好后提交，只暂存这些文档。

完成标准：标准文档都已存在并在用户审查后提交；STATUS 第一行是 `初始化`。

## 3. 摸底（只用于已有项目）

在初次使用ata，但是已经具有一定规模的项目中，你需要建立起对这个项目的全面认知，并向用户汇报当前项目的各方面的情况，所以，你需要在完成第二步之后：

派出一张摸底任务卡，让 worker 整理项目结构、构建和测试命令、现有文档、未完成的工作，写在汇报里。项目有源码时，同一张卡按 `references/docs/module-map.md` 生成 `docs/module_map.md`：写入范围只有这一个文件；项目里已经有地图的，不覆盖，在汇报里说明它和写法的差距。卡片按 `references/docs/task-card.md` 写，主线字段写「初始化」。你只读它的结论，不自己通读。

完成标准：摸底卡已被你和用户确认正式验收，你基本掌握了写总计划所需的现状；项目有源码时，也有了源码地图。

### 4. 和用户对齐开发总目标和方向

这一步很重要，你需要和用户讨论，同时也积极的向用户提问，以此来确认以下信息：

- **项目定位**：项目的目标使用场景，功能，用户，即“用来干什么，能干什么，给谁用”；
- **要实现的功能范围**：哪些是明确需要实现的，哪些是候选实现，又有哪些是明确不予实现；
- **实现方案**：项目计划使用的编程语言，技术栈和设想的项目架构；
- **构建路线**：项目功能的先后实现顺序，阶段划分。

流程：

1. 预先定位到`docs/scratchpad.md`，向用户提问；
2. 一次只问两到三个问题，每个问题给出你的推荐方案，但不要擅自替用户做决定；
3. 每轮问题得到用户的回答后，立刻记录到`docs/scratchpad.md`中，再继续下一轮的针对性的问答；
4. 一直提问到能够系统性的完整回答上面需要确认的信息。

tips: 环境里有专门的追问类 skill（如 grilling）时，积极调用。

**红线**：

- 不要为了提问而提问，一切问题以能够获取到足够撰写项目总计划的信息出发；
- 不要过度追问，把握好问题的尺度和你需要获取的信息的范围。

收集到足够的信息后，向用户汇报并让用户审查`docs/scratchpad.md`，用户审查通过后，就进入下一阶段。

## 5. 撰写项目总计划

这一阶段你需要基于上一阶段的`docs/scratchpad.md`开始正式撰写`docs/PROJECT_PLAN.md`。

流程：

1. 基于速记本确认下的信息，按 `references/docs/project-plan.md`的指导要求，开始撰写`docs/PROJECT_PLAN.md`；
2. 将撰写好的`docs/PROJECT_PLAN.md`交由用户审查，直至通过；
3. 在`docs/PROJECT_PLAN.md`通过用户审查后，将`docs/scratchpad.md`进行归档冻结；
4. 更新`AGENTS.md`，补上项目定位；
5. 更新`docs/STATUS.md`，更新项目实时状态；

## 6. 待命

上一阶段的任务完成后，就进入该workflow的尾声了，先清晰明了的向用户汇报当前的总体情况，再脱离当前workflow，交由用户决定下个流程，在进入下个workflow后，不要再代入此workflow，避免造成任务混乱。
