# 施工：派工、验收和主线收口

适用：STATUS 当前主线为「施工中」。

开始前读：STATUS 第一行指向的计划文档；第一次写任务卡前读 `references/docs/task-card.md`。

## 注意

因为这个阶段是项目的实际施工阶段，所以难免会有计划方案和实际情况不符的情况，以及用户在实际构建过程中，可能随时会更改方案或做出重要决定，
这时就需要你读取`references/docs/decisions.md`，按照其中的指导将用户的决策记录下来。

## 标准工作流程

### 1. 前置启动

从计划里取下一个未完成的交付项，按 `references/docs/task-card.md`「任务卡体量要求」决定派一张还是几张卡。前置条件没满足时（用户的决定、账号、依赖的卡），先处理或问用户，不派注定受阻的卡。

完成标准：确定了任务卡的数量和实现范围。

### 2. 编写任务卡

按`references/docs/task-card.md`的指导写卡、登记、提交，然后向用户简单汇报：

- 本次任务单规定的实现范围；
- 预计涉及的文件；
- 预计的工作量；
- 预计的产物。

接着用户在审查完任务单表示通过后，才可正式派发。

### 3. 派发任务单

任务单通过用户审查后，在 STATUS 登记这张卡并把下一个卡号加一，提交（`docs: dispatch T-###`），然后向用户输出转手的话：

> 你现在是 ata 的 worker。读取 `docs/tasks/T-###.md`，...。

后续内容可以自行根据实际情况灵活添加，只要可以更好的指导worker开始任务。

完成标准：用户拿到了转手的话并已经发放给worker。

### 4. 验收

接收到用户发来的worker报告后：

1. **对照**：用 `git status --short` 和 `git diff --stat` 对照汇报的改动清单。改了写入范围以外的文件时，汇报里说明了理由且你认可的才保留，否则退回。
2. **证据**：按 `references/master.md`「验证三档」定档：默认采信、抽查证据或重跑。
3. **判断审查**：读 diff 的实质部分，确认：
   - 达成了卡片目标，满足完成标准；
   - 符合项目规范（如 `docs/code_spec.md`）和计划里的契约；
   - 没有擅自改契约，没有留下新旧两套做法；
   - worker 标出的疑点都有了结论。
4. **结论**：
   - **通过**：在卡片追加验收记录，状态改为已完成；这个交付项的卡全部通过后，在计划里填「完成」（`references/docs/plan.md`）；处理汇报里的建议；更新 STATUS；提交 `T-###: <结果>`。使用任务分支时再合并，复验规则见 master.md。
   - **返工**：按下方的第五节内容进行处理。
   - **受阻**：需要用户处理的，告诉用户，记进 STATUS「阻塞」；不依赖它的卡照常推进。

汇报里的建议：

- 文档变更建议：你判断成立的，直接改对应文档。
- 候选经验：你判断值得记的，写进 `docs/ata/inbox.md`（`references/docs/practices.md`）；你自己在派工、验收中发现的，也记在那里。

完成标准：卡片状态、计划里的交付项和 STATUS 三处一致，并且已经提交。

### 5. 返工

触发条件：如果在验收环节，你发现worker的工作成果为达到目标，存在功能缺陷，bug等情况，不能标记为通过需要返工时。

1. 先向用户简单说明情况，为什么不能验收，哪里出了问题，需要修复哪些问题，让用户决定是否安排返工；
2. 用户确认授权后，按`references/docs/task-card.md`的指导，在任务卡的结尾添加上“验收结果”和“需要返工项”，然后交给用户需要转发给worker的话。

模板参考：

> “审查结果：需要返工，继续执行`docs/tasks/T-###.md`，按任务卡中的返工安排执行针对性的返工...。”

### 6. 归档

验收通过后，卡片状态改为「已完成」，保留在 `docs/tasks/` 直到本主线收口。收口时统一删除，之后从 Git 历史查（`git log -- docs/tasks/T-###.md`）。

### 7. 主线收口

计划里的交付项全部完成后：

1. **主线验收**：对照计划的验收标准判断。需要完整测试或构建时，派一张验收卡，不自己跑。
2. **用户确认**：向用户汇报结果，确认本主线完成。
3. **文档**：
   - 计划文档整理为完成形态，之后冻结（`references/docs/plan.md`）；
   - 总计划路线图把本主线改为已完成；
   - 删除本主线已完成的任务卡；
   - README 或源码地图没跟上的，派一张卡补上；大规模重构的主线，这张卡还要按现在的代码校正整份地图；
   - 需要时派一张文档审查卡（环境里有文档审查类 skill 时，让 worker 使用），审查报告交给用户审阅。
4. **经验**：按 `references/docs/practices.md`「提炼」整理收件箱。
5. **下一条主线**：STATUS 当前主线改为待定，按 `workflows/planning.md` 和用户确定下一条。
6. **提交**；推送按授权。

完成标准：路线图、计划文档、任务卡目录和 STATUS 互相一致，并且已经提交。
