# 施工：派工、验收和主线收口

适用：STATUS 当前主线为「施工中」。

开始前读：STATUS 第一行指向的计划文档；第一次写卡前读 `references/docs/task-card.md`。

## 1. 选下一张卡

从计划里取下一个未完成的交付项，按 master.md 5.5 确定卡的大小。前置条件没满足时（用户的决定、账号、依赖的卡），先处理或问用户，不派注定受阻的卡。

完成标准：确定了这张卡的范围；或者已经告诉用户卡在哪里。

## 2. 写卡并派发

按 `references/docs/task-card.md` 写卡、登记、提交，然后告诉用户转手的话。

worker 施工期间你也可能提交，例如更新 STATUS。这时只暂存你自己改的文档，不用 `git add .` 或 `git add -A`，免得把 worker 做了一半的改动提交进去。

完成标准：卡片已提交；用户拿到了转手的话。

## 3. 验收

worker 汇报后：

1. **对照**：用 `git status --short` 和 `git diff --stat` 对照汇报的改动清单。改了写入范围以外的文件时，汇报里说明了理由且你认可的才保留，否则退回。
2. **证据**：按 master.md 5.6 定档：默认采信、抽查证据或重跑。
3. **判断审查**：读 diff 的实质部分，确认：
   - 达成了卡片目标，满足完成标准；
   - 符合项目规范（如 `docs/code_spec.md`）和计划里的契约；
   - 没有擅自改契约，没有留下新旧两套做法；
   - worker 标出的疑点都有了结论。
4. **结论**：
   - **通过**：在卡片追加验收记录，状态改为已完成；计划里对应的交付项标 `✓ T-###`；处理汇报里的建议；更新 STATUS；提交 `T-###: <结果>`。使用任务分支时再合并，复验规则见 master.md 5.6。
   - **返工**：在卡片追加返工项，状态改为返工中，告诉用户转手的话。
   - **受阻**：需要用户处理的，告诉用户，记进 STATUS「阻塞」；不依赖它的卡照常推进。

汇报里的建议：

- 文档变更建议：你判断成立的，直接改对应文档；涉及已确认内容的，按 `workflows/ad-hoc.md` 的变更分级处理。
- 候选经验：你自己的写进 `docs/ata/notes/master.md`；worker 写在「建议」里的，你判断值得记的写进 `docs/ata/notes/worker.md`（写法见 `references/docs.md`「项目实践记忆」）。一次性的现象不记。

完成标准：卡片状态、计划里的交付项和 STATUS 三处一致，并且已经提交。

## 4. 主线收口

计划里的交付项全部完成后：

1. **主线验收**：对照计划的验收标准判断。需要完整测试或构建时，派一张验收卡，不自己跑。
2. **用户确认**：向用户汇报结果，确认本主线完成。
3. **文档**：
   - 计划文档整理为完成形态（`references/docs.md`）；
   - 总计划路线图把本主线改为已完成；
   - 删除本主线已完成的任务卡；
   - 需要时派一张文档审查卡（环境里有文档审查类 skill 时，让 worker 使用），审查报告交给用户审阅。
4. **经验**：notes 积累较多或同类问题反复出现时，派一张提炼卡（`references/docs.md`「项目实践记忆」）。
5. **下一条主线**：STATUS 当前主线改为待定，按 `workflows/planning.md` 和用户确定下一条。
6. **提交**；推送按授权。

完成标准：路线图、计划文档、任务卡目录和 STATUS 互相一致，并且已经提交。
