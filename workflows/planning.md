# 规划：为一条主线写详细的实现计划

适用：STATUS 当前主线为「规划中」，或者当前主线待定。

主线可以是路线图里的一个阶段，也可以是计划外的一项较大工作，例如审查整改、重构或调研。

开始前读：总计划里本主线的路线图条目和相关章节（不通读）；本主线已有的计划草稿；`references/docs.md` 中计划文档的写法。

## 1. 确定主线

当前主线待定时，和用户确定下一条：路线图里的下一阶段，或者恢复一条暂停的主线（恢复前对照暂停期间新增的决定，重审挂起的卡）。确定后在 STATUS 写上主线名和状态，路线图对应条目改为进行中。

完成标准：STATUS 第一行写明了主线名，状态为规划中。

## 2. 对齐

和用户逐个讨论，直到足以写计划：

- 本主线交付什么能力或产物，做到什么程度算完成；
- 技术路线、框架、跨模块契约；
- 明确不做什么；
- 需要用户决定的取舍。

一次只问一个问题，并给出你的推荐。环境里有专门的追问类 skill（如 grilling）时，可以使用。讨论需要事实支撑时（现有代码怎么组织、某个方案是否可行），派一张只读调研卡，不自己通读。

用户的决定当场写进 `docs/decisions.md`。

完成标准：上面每一项都有用户确认的答案，或者写明了留到施工中再定的理由。

## 3. 写计划

阶段计划写在 `docs/phaseN_plan.md`，其他主线写在 `docs/<主题>_plan.md`，写法见 `references/docs.md`。另外两点：

- 交付项按 master.md 5.5 的粒度列出，每项写清验收方式。施工时一项对应一张卡，验收后在这一项后面标 `✓ T-###`。
- 只写已确认的内容。未决的事列为待定，不写成定论。

完成标准：用户确认了计划。

## 4. 转入施工

STATUS 第一行改为 `<主线名> · 施工中 · 计划：<路径>`，提交，然后按 `workflows/execution.md` 派第一张卡。

完成标准：STATUS 已提交，并指向本主线的计划。
