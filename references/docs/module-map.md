# 源码地图写法

`docs/module_map.md` 让 agent 不通读仓库就能定位任务涉及的文件：master 写任务卡时，用它定「必读」和写入范围；worker 施工时，用它找到要读、要改的文件。地图只回答"这件事在哪些文件里"；文件里具体怎么做，读代码确认。

维护：

- 项目有了源码就建：已有项目由初始化的摸底卡生成，新项目由第一张产出源码的卡建立。
- 新增、删除、重命名文件，或者文件管的事变了，由做这项改动的那张卡同步更新。
- 大规模重构的主线，施工期间以代码为准，地图暂不更新，收口时派一张卡统一校正。

## 1. 模板

文件在约 30 个以内时，不分组，用一张表按目录排列，整份读完也不贵：

```markdown
# 源码地图

> 用来定位文件；文件里具体怎么做，读代码确认。
> 新增、删除、重命名文件，或者文件管的事变了，由同一张卡更新本文。

| 文件 | 管什么 |
|---|---|
| `<路径>` | <管什么> |

测试：<测试和源码的对应规则>

## 常见改动

- <一类改动>：<要同时改的文件>
```

文件多了以后，派一张卡改成分组的形式。分组只改地图，不动代码：

```markdown
# 源码地图

> 先读索引，再读相关的组；文件里具体怎么做，读代码确认。
> 新增、删除、重命名文件，或者文件管的事变了，由同一张卡更新本文。

## 索引

| 组 | 管什么 |
|---|---|
| <组名> | <一句话> |
| 公共 | <几组共用的部分> |

测试：<测试和源码的对应规则>

## <组名>

规格：<这组有领域规格时写路径；没有就删掉这一行>

- `<路径>`：<管什么>
- `<目录>/`：<管什么>

## 公共

- `<路径>`：<管什么>

## 常见改动

- <一类改动>：<要同时改的文件或组>
```

## 2. 各节写法

### 2.1 条目

- 每个源码文件和测试文件，都要能在地图里找到它所属的一行，单列或者合并都可以。覆盖完整，地图才可信。
- 一行写这个文件管什么，20～40 字，不写行为细节和函数名。行为细节每张卡都可能改，写进地图，地图很快就会过时；找函数和类，搜索比地图准。
  - 不好：「`store.py`：会话存储；`save()` 先写临时文件再原子替换，失败重试三次后抛出 `StoreError`……」
  - 好：「`store.py`：会话记录的保存、读取和迁移」
- 同一目录下作用相同的文件，合成一行，例如「`exporters/`：各种导出格式，一种格式一个文件」。
- 测试和源码按固定规则对应时，在「测试」行写一条规则；对应不上的测试文件，写进它测试的那一组。

### 2.2 分组

- 按任务会怎么描述来分：组名用计划和任务卡描述功能时的说法，例如「用户登录」「报表导出」，不用技术分层的名字。
- 一个文件只进一组，也就是它主要服务的那个功能；几组共用的进「公共」。
- 分组是从现有代码里归纳出来的，不需要事先设计，也不需要和目录结构一致。
- 这组有领域规格时，在组下写规格路径，方便写卡时一起列进「必读」。

检验：「拿计划里的几项交付试一试：每项只读一两组，就能定出写入范围吗？要读三组以上的，调整分组，或者在「常见改动」里补一条。」

### 2.3 常见改动

只写跨组、靠搜索不容易发现的联动，例如新增一种命令，除了实现本身，还要在注册表里登记、在帮助文本里加说明。写入范围漏掉的文件，大多出在这里。没有这样的联动时，写「无」。

## 3. 不写什么

- 行为细节、函数和类：读代码或搜索。
- 目标、进度、讨论和历史。
- 生成的文件、依赖目录、构建产物，以及还不存在的文件。

## 4. 检验

每次更新后，对照 `git ls-files` 检查两件事：列出的源码和测试文件都能在地图里找到；地图里写的路径都还存在。
