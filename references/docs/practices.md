# docs/ata/ 写法：实践手册和收件箱

`docs/ata/` 保存 master 和 worker 在本项目里积累的工作经验：实践手册放已经提炼、仍然有效的做法；收件箱放还没提炼的候选经验。三份文件都由 master 维护。worker 的经验写在任务卡汇报的「建议」里，由 master 判断记不记。

```text
docs/ata/
├── master_practices.md   master 的实践手册
├── worker_practices.md   worker 的实践手册
└── inbox.md              候选经验的收件箱
```

## 实践手册

模板（worker 那份把 Master、master 换成 Worker、worker）：

```markdown
# Master 项目实践手册

本文记录 master 在本项目中已经提炼、仍然有效的实践，在本项目内优先于角色卡的默认做法。当前暂无条目。
```

- 每份只写给一个角色：master 在会话启动时读自己的，worker 开工时读自己的。
- 每条写成可以照着做的规则，一两行。不写经过、日期和出自哪张卡。
- 整理时可以重写、合并、删除条目；失效的直接删掉，需要追溯时查 Git。
- 只写本项目特有的做法。对所有项目都成立的，作为 ata 的修改建议告诉用户；项目的技术事实和代码规范，写进它们的主文档。

检验：「下一个会话读到这条，会照着做出不同的动作吗？不会，就不该在手册里。」

## 收件箱

模板：

```markdown
# 候选经验收件箱

> 由 master 维护。这里的条目是候选，不是规则，任何会话都不按它行事。
> 格式：`- YYYY-MM-DD · 来源 · 现象和证据位置 → 建议去向`

当前暂无条目。
```

- 由 master 写，两个来源：自己在派工、验收中发现的；worker 写在「建议」里、你判断值得记的。
- 每条 1～3 行。来源写任务卡编号、master 或用户；证据写位置（卡片、日志、提交），不贴原文。
- 一次性的现象不记。
- 收件箱只在提炼时读，平时不读。

检验：「这条经验在下一个相似的场景里，能改变谁的什么做法？说不出来就不记。」

## 提炼

出现下面任何一种情况，就提炼一次：

- 主线收口；
- 同类问题出现了第二次；
- 一次就代价很大：数据损失、安全问题、大范围返工；
- 用户纠正了某个做法。

做法：

1. 逐条分诊：合并重复的，删掉偶发的和已经失效的，剩下的按下表定去向。证据要读很多代码或日志时，派一张只读卡核对，你只读结论。
2. 把要写入的改动以 diff 的形式交给用户，用户确认后写进去向文档。
3. 删掉处理过的条目。收件箱不留历史，需要追溯时查 Git。

| 经验 | 去向 |
|---|---|
| 所有会话都要遵守的红线、验证要求、环境限制 | `AGENTS.md`「工程原则」 |
| 代码和测试怎么写 | 项目的代码规范；没有时写进 `AGENTS.md`「工程原则」 |
| 某个领域的行为 | 领域规格 |
| master 怎么派工、验收 | `master_practices.md` |
| worker 怎么施工、汇报 | `worker_practices.md` |
| 对所有项目都成立的 ata 改进 | 告诉用户，作为 ata 的修改建议，不写进本项目 |

能用测试或 lint 检查的规则，派卡做成检查，比写成文字可靠。

## 从旧版升级

项目里有旧版 ata 的 `docs/ata/notes/`，或者别处已经有经验收件箱时：把仍有价值的条目按收件箱的格式迁进 `inbox.md`，和用户确认后删掉旧文件。
