# 领域规格写法

领域规格记录某个领域已经确认、现在仍然有效的行为规则，例如界面的交互和显示、对外协议、文件格式。规则细到计划里写不下，又要跨主线长期遵守时，才单独建一份，文件名体现领域即可，例如 `docs/export_format.md`。

master 把和用户确认过的规则写进去；需要从现有代码整理出规格时，派一张卡。

## 模板

规格的内容因领域而异，只固定开头：

```markdown
# <领域>规格

> 本文是<领域>行为的主文档。改变这里的规则，先经用户确认。

## 范围

<本规格管哪些行为；相邻但不归本文管的，指向哪份文档>

## <规则分类>

- <在什么情况下，系统怎么表现>
```

## 写法

- 写规则：在什么情况下，系统应该怎么表现。需要时配参考图或示例数据。
- 只写用户确认过的规则。讨论中的结论先记在 `docs/scratchpad.md`。
- 只写现行的规则：规则变了直接改，不保留旧版，不并列新旧两套。改的理由在 decisions，经过在 Git 历史。
- 改变已确认的规则，按 `workflows/ad-hoc.md` 的变更分级处理。
- 和主线计划的分工：计划的「契约」只管这一条主线；跨主线长期有效的规则写在规格里，计划只写路径。

检验：「worker 只读这份规格，能判断实现出来的行为对不对吗？」

## 不写什么

- 路线图、任务和进度。
- 实现方式和文件位置：在代码和源码地图。
- 讨论过程和被否决的方案。
