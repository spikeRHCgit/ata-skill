# 主线计划写法

主线计划写一条主线的目标、交付项、契约和验收，是派卡和验收的依据。路线图里的阶段和计划外的主线都用它。master 和用户对齐实现方案后写，通过用户审查才生效。

生效后，施工中只在交付项验收时填「完成」；改目标、范围、契约或验收，属于推翻已确认的内容，先经用户确认。主线收口时整理成完成形态，之后冻结。

文件名：路线图里的阶段写在 `docs/phaseN_plan.md`，N 是路线图里的序号；项目计划外的主线（审查整改、重构等）写在 `docs/<主题>_plan.md`。

## 模板

```markdown
# <主线名>计划

## 目标

<客观概述当前主线的目标，1～3 句，要求条理清晰>

## 范围

要实现：

- <…>；
- <…>。
...

不要实现：

- 不做：<容易被顺手做掉、需要明确排除的>
...

## 交付项

### 1. <名称>

- 前置：<无|交付项 N>
- 要实现：
  - <这一项完成后能做到什么，包括边界情况和失败时的表现>
  ...
- 实现方式：
  - <落在哪些模块，关键的接口、数据结构和数据格式，要引入的依赖>
  ...
- 验收：
  - <可观察的结果>
  ...
  - 验证：`<命令>`
  - 用户验收：<需要用户亲自确认的项目|无>
- 完成：<未完成|✓ T-###、T-###>

### 2. <名称>

...

## 契约

- <交付项之间、模块之间要遵守的接口、数据格式和行为约定>

## 验收

- <几个交付项合起来才能观察到的结果>
...
- 最终验证：`<命令>`
- 用户验收：<整条主线完成后需要用户亲自确认的项目|无>

## 待定

- <还没定的问题>：<在哪个交付项之前要定>
```

## 各节写法

- 只写用户确认过的内容。讨论还没结束时，中途的结论记在 `docs/scratchpad.md`。
- **范围**：「不做」只写容易被误做的，没有就删掉这一行。
- **交付项**：见下一节。
- **契约**：只写跨交付项、跨模块要遵守的约定。细到某个领域的行为规则，写进领域规格，这里写路径。
- **验收**：只写交付项各自验收以外的部分，交付项里已写的不重复：
  - 几个交付项合起来才能观察到的结果，例如端到端的完整流程；
  - **最终验证**：收口时的完整测试和构建命令，不在每个交付项里重复跑；
  - **用户验收**：整条主线完成后需要用户亲自确认的项目，没有写「无」。

  交付项全部完成，并且通过这一节，整条主线才算验收通过。
- **待定**：只列确实要等施工中的事实才能定的，每条写明最晚在哪个交付项之前定。定了就写进对应的节，删掉这一条，并在 `docs/decisions.md` 追加一条。
- **从需求简报迁入**：路线图里的阶段在总计划里有需求简报时，已确认的条目直接写进计划；倾向和留给阶段计划的条目，和用户逐条定下来再写。计划通过用户审查后，才删掉总计划里的简报。

检验：「只读这份计划，能写出每个交付项的卡，并验收整条主线吗？」

## 交付项写法

交付项把主线要实现的内容分成几部分，每部分写清楚实现什么、怎么实现、怎么验收。master 据此派卡和验收，worker 拿到的卡里不应该还有方案要设计。

### 划分

- 一项是一个能单独验收的能力：做完以后，不依赖后面的项，就能观察到它的效果。不按文件、字段或按键拆。
- 一项要分好几批才能做完时，先检查它是不是几个能单独验收的能力挤在了一起；是的话拆成几项。
- 范围「要实现」里的每一条，都落在某一个交付项里。
- 按依赖排序，前面的项先做；**前置**写这一项要等哪些项验收后才能开始，没有写「无」。
- 施工时一项由一张或几张卡完成，卡怎么拆见 `references/docs/task-card.md`。

### 要实现

写这一项完成后能做到什么，一条一个行为。除了正常流程，写清边界情况和失败时的表现：worker 遇到计划没写的情况只能自己猜，猜错了就是返工。

### 实现方式

写对齐时和用户定下的方案：落在哪些模块、要不要新增模块，关键的接口、数据结构和数据格式，要引入的依赖。

- 写到跨模块、影响用户可见行为、改变契约或数据格式的程度；模块内部怎么写，留给 worker。
- 只在这一项里用到的接口写在这里；几个交付项共用的写在「契约」，这里写「见契约」。
- 施工步骤和文件清单写在任务卡，不写在这里。

### 验收

写这一项做到什么程度算完成：

- 每条写一个可观察的结果，能判断是或否，不写「实现 X」「结构清晰」这类没法判断的话；
- **验证**写自动化检查的命令；
- **用户验收**写需要用户亲自确认的项目，例如真实终端里的显示和操作，没有写「无」。

### 完成

派卡前写「未完成」。这一项的卡全部验收通过后，改成 `✓` 加卡号，多张卡依次列出。

检验：「只读这一项，能直接拆出任务卡，并且不用再问用户怎么实现吗？」

## 完成形态

主线验收通过后，把计划整理成四节：

1. **目标**：这条主线形成了什么能力。
2. **已交付**：最终交付的能力。做过又撤掉的不算。
3. **实现概况**：这些能力由哪些模块实现、怎么协作。比总计划细，不复制源码地图。
4. **验收结论**：通过了哪些验收，涉及哪些任务卡（卡片删除后从 Git 历史查）。

以后的主线也要遵守的契约，整理时迁进领域规格。总计划处于半冻结状态，不因为主线收口而修改。

整理完就冻结，不再修改。以后的主线改变了这里的实现，也不回来补注：现在的行为以代码、源码地图和规格为准，变化的经过在后来那条主线的计划和 Git 历史里。

检验：「后来的人只读完成形态，能知道这条主线交付了什么、大致在代码的哪里吗？」

## 不写什么

- 任务卡层面的细节：施工步骤、文件清单。
- 当前进度：在 STATUS。计划里只有交付项的「完成」。
- 讨论过程和理由：对齐时的在速记本的归档里，施工中的在 decisions；这里只写结论。
- 某个领域的行为细则：在领域规格。
- 施工流水、worker 汇报原文、按日期的进度。
