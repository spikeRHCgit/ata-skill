# PROJECT_PLAN.md 写法

`docs/PROJECT_PLAN.md` 是项目级的计划：定位与目标、阶段路线图、各阶段需求简报、产品范围、架构和项目级验收。master 在初始化时和用户对齐后写。

总计划通过用户审查后处于半冻结状态，只在两种情况下修改：

- 路线图里阶段的状态变化，连同这一阶段的计划列和需求简报（见「阶段路线图」「各阶段需求简报」）；
- 用户明确要求改变项目方向，按 `workflows/ad-hoc.md` 的 L2 处理。

计划外的主线、施工中的发现和调整，都不改总计划。

本文只写跨阶段都成立的内容：只关系到一个阶段的，写进这个阶段的需求简报或主线计划。

## 模板

```markdown
# 项目总计划

> 由 master 维护，只写跨阶段都成立的内容。
> 当前进度在 `docs/STATUS.md`。
```

## 各节写法

没有内容的节写「无」，不删节，这样读的人能确认这一项已经检查过。

检验：「这条内容跨阶段都成立吗？只关系到一个阶段的，写进这个阶段的简报或计划。」

### 定位与目标

**用途**、**用户**、**目标**各一两句。`AGENTS.md` 的项目定位是它的摘要，这一节改了，同步修改 AGENTS.md。

### 阶段路线图

一个阶段一行，按序号排列。计划外的主线不进路线图，它的状态在 STATUS，内容在它自己的计划里。

- **阶段**：写序号和名称，序号和计划文件名 `docs/phaseN_plan.md` 的 N 一致。
- **状态**的取值：
  - `未开始`：还没开始规划；
  - `进行中`：当前主线，从确定开始规划起，到收口为止；
  - `已暂停`：被其他主线打断，断点在 STATUS 的「暂停的主线」；
  - `已完成`：主线已收口，计划已整理成完成形态。
- 状态跟着主线的变化当场改：确定开始规划时改为进行中（`workflows/planning.md` 第 1 节）；被打断时改为已暂停，恢复时改回进行中；收口时改为已完成。同一时间最多一行是进行中；当前主线是计划外的主线时，没有一行是进行中。
- **目标**：一句话，是这一阶段需求简报里「子阶段目标」的摘要。
- **计划**：主线计划通过用户审查后写计划路径；在那之前写「见需求简报」。
- 还没写主线计划的阶段，不直接派施工卡，先按 `workflows/planning.md` 规划。

### 各阶段需求简报

需求简报按阶段保存需求，从初始化一直保留到这个阶段的计划落地：

- **建立**：初次撰写总计划时，路线图里的每个阶段都写一份，包括第一阶段，按路线图的顺序排列，标题写「阶段 N：<名称>」，和路线图的那一行对应。
- **保留**：阶段还没推进到时，简报一直留在这里，作为这个阶段规划时的依据；中途只有用户明确改变方向时才修改。
- **清除**：推进到某个阶段时，按 `workflows/planning.md` 规划，把这份简报整理进它的主线计划（`references/docs/plan.md`「从需求简报迁入」）。主线计划通过用户审查、正式落地后，才删掉这份简报，路线图的计划列改成计划路径。还没落地时简报不动，规划中断也不会丢内容。

所以任何时候，计划列写「见需求简报」的阶段，下面都有一份对应的简报。

每份简报的写法：

- **子阶段目标**：一两句写这个阶段完成后能做到什么。
- **具体实现范围**：这个阶段要实现的功能和要达到的目标，一项一条。产品范围「核心」里的每一项，都要落在某个阶段的实现范围里，或者已经由完成的阶段实现。
- **已确认**、**倾向**、**留给子阶段计划的正式讨论阶段**三档，记录对实现范围里各项的具体要求和取舍：
  - 已确认：用户确认过，阶段计划必须遵守；出自决定的注明 D-###；
  - 倾向：讨论过、还没定，规划时再和用户确认；
  - 留给子阶段计划的正式讨论阶段：知道要定、现在不定，到这个阶段规划时再讨论。
- 实现范围写「做什么」，三档写「做成什么样、怎么做」；同一条内容不在两处重复。
- 某一项没有内容时写「无」。
- 推翻已确认的条目，属于改变项目方向，先在 `docs/decisions.md` 追加新决定（`workflows/ad-hoc.md` 的 L2）。
- 整理进主线计划时：子阶段目标写进计划的「目标」，具体实现范围写进「范围」的「做」，已确认的条目直接写进计划，另外两档在规划时逐条和用户定下来。

简报的作用：和用户讨论出的后续需求，在阶段开始前有地方长期保存。没有它，精简总计划时，已确认的后续需求容易被当成细节删掉，到阶段开始时只能重新讨论。

检验：「到这个阶段开始规划时，只读这份简报，还需要再问用户已经确认过的内容吗？」

### 产品范围

- **核心**：一定要做的。
- **候选扩展**：以后可能做、现在不排期的。用户决定把它排进某个阶段时，从这里移到核心。
- **不做**：明确排除的，出自决定的注明 D-###。

### 架构

- **技术栈**：项目用的语言、框架、运行环境和关键依赖。
- **总体结构**、**核心子系统**、**边界**：只写跨阶段都要遵守的结构和约束。某个阶段内部的结构写在它的主线计划里，具体的接口和行为写在领域规格里。

### 项目级验收

整个项目做到什么程度算完成，每条写可观察的结果。每个阶段的验收写在阶段计划里。

## 初次撰写

- 依据速记本写：每条已确认的内容写进它所属的节；只关系到某一个阶段的，写进这个阶段的需求简报。
- 路线图里的每个阶段都写一份需求简报，包括第一阶段。
- 第一阶段就是第一条主线，在路线图里标为进行中，计划列写「见需求简报」；其余阶段标为未开始。
- 已有项目：写现状和后续路线。架构写现有的结构；路线图从接下来要做的写起，做到一半的工作作为第一阶段。

## 不写什么

- 当前主线和进度：在 STATUS，路线图里只有各阶段的状态。
- 计划外的主线：在 STATUS 和它自己的计划里。
- 决定的理由：在 decisions，这里只写结论和编号。
- 工程原则和代码风格：在 `AGENTS.md` 或项目的代码规范。
- 文件和目录：在源码地图。
- 某个领域的具体行为：在领域规格。
- 阶段的施工方案和任务：在主线计划和任务卡。
- 讨论过程：在速记本的归档里。
