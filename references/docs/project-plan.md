# PROJECT_PLAN.md 写法

`docs/PROJECT_PLAN.md` 是项目级的计划：目标、阶段路线图、产品范围、架构和项目级验收。master 在初始化时和用户对齐后写；之后只在主线开始或收口、用户改变项目方向时修改。

## 模板

```markdown
# 项目总计划

## 定位与目标

<这是什么项目，给谁用，要达成什么>

## 阶段路线图

| 阶段 | 状态 | 目标 | 计划 |
|---|---|---|---|
| 1. <名称> | 进行中 | <一句话> | `docs/phase1_plan.md` |
| 2. <名称> | 未开始 | <一句话> | 见下方简报 |

### 阶段 2 需求简报

- 已确认：<条目>（D-###）
- 倾向：<条目>
- 留给阶段计划：<条目>

## 产品范围

- 核心：<…>
- 不做：<…>
- 候选扩展：<…>

## 架构

<总体结构、核心子系统、子系统之间的边界>

## 项目级验收

<整个项目做到什么程度算完成>
```

## 各节写法

- **定位与目标**：几句话。`AGENTS.md` 的项目定位是它的摘要。
- **阶段路线图**：
  - 一个阶段一行：顺序、状态（未开始、进行中、已完成）、一句话目标、计划入口。还没写计划的阶段，计划列写「见下方简报」。
  - 状态只在主线开始和收口时改。计划外插入的主线也加一行（`workflows/ad-hoc.md` 第 4 节）。
  - 还没写主线计划的阶段，不直接派施工卡，先按 `workflows/planning.md` 规划。
- **需求简报**：
  - 每个还没写计划的阶段一份，放在路线图下面。
  - 条目分三档：已确认（用户确认过，阶段计划必须遵守；出自决定的注明 D-###）；倾向（讨论过、还没定，规划时再确认）；留给阶段计划（知道要定、现在不定）。
  - 推翻已确认的条目，先在 `docs/decisions.md` 追加新决定（`workflows/ad-hoc.md` 的 L2）。
  - 阶段开始规划时，简报整体迁进它的计划，然后从这里删掉，计划列改成计划路径。

  简报的作用：初始化时和用户讨论出的后续需求，有地方长期保存。没有它，精简总计划时，已确认的后续需求容易被当成细节删掉，到阶段开始时只能重新讨论。
- **产品范围**：核心是一定要做的；不做是明确排除的；候选扩展是以后可能做、现在不排期的。
- **架构**：总体结构、核心子系统和它们之间的边界。
- **项目级验收**：整个项目做到什么程度算完成。每个阶段的验收写在阶段计划里。

检验：「这条内容跨阶段都成立吗？只关系到一个阶段的，写进这个阶段的简报或计划。」

## 不写什么

- 当前主线和进度：在 STATUS。
- 决定的理由：在 decisions，这里只写结论和编号。
- 工程原则和代码风格：在 `AGENTS.md` 或项目的代码规范。
- 文件和目录：在源码地图。
- 某个领域的具体行为：在领域规格。
- 阶段的施工方案和任务：在主线计划和任务卡。
