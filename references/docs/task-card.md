# 任务卡写法

任务卡（`docs/tasks/T-###/T-###.md`）把一项任务交给 worker：做什么、改哪里、做到什么程度算完。worker 只拿这张卡施工，你按它验收。本文写给 master，第一次写卡前读。worker 怎么执行和汇报，写在 `references/worker.md`。

## 位置与编号

- 卡片放在 `docs/tasks/T-###/T-###.md`。编号全局递增，取 STATUS 记录的「下一个卡号」，用过的编号不再复用。
- 同一任务的过程文件放在卡片同目录：worker 本轮汇报为 `worker-01.md`，master 对应的审查报告为 `review-01.md`，返工要求为 `rework-01-request.md`。轮次用两位数递增；第一次返工对应 `worker-02.md` 和 `review-02.md`。
- 每份过程文件只写本轮的要求或结论，用相对路径关联依据，不复制任务卡或之前的报告。卡片只保留任务定义、当前状态和最终收口摘要。
- 从新卡起采用这个结构，已有卡片不迁移。
- 验收提交的信息以 `T-###:` 开头，这样 `git log --oneline` 就是完成记录。

## 模板

> 该模板是基于代码开发任务的特化模板，在用户向你指示除代码开发之外的任务时，你可以自由的调整任务卡的内容，结构等，以达到符合任务要求的效果。

```markdown
# T-###：<标题>

状态：未定稿|执行中|阻塞中 · 主线：<主线名|计划外> · 交付项：<计划路径> 交付项 N|无 · 风险：常规|高

## 目标概览、

<完成后能得到哪些实际的成果，1～3 句>

## 必读文件

- <路径>：<要从中拿到什么>
...

## 推荐启用 skill

- <skill 名>：<为什么用；没有就删掉整节>

## 写入范围

- 允许：
  - <文件或目录>
  - `docs/tasks/T-###/worker-01.md`：本轮汇报
  ...
- 禁止：<本卡特有的越界风险>

## 具体实现目标

- <这一步完成后能做到什么，包括边界情况和失败时的表现>
...

## 具体实现方案

- <改动涉及哪些模块；关键的接口签名、数据结构或数据格式；要引入的依赖>
...

## 实现要求

- <一个要求：要改的接口或数据格式、要遵守的契约或规范条款、已知的坑>
...

## 完成标准

- <可观察的结果>
...
- 验证：`<命令>`


```

## 各节写法

### 状态行

- **状态**只由你修改，取值见「生命周期」。
- **主线**：不属于任何主线的卡写「计划外」。
- **交付项**：写计划路径和交付项编号。一个交付项拆成几张卡时，加上「第 k 步」；调研、审查卡不对应交付项的写「无」。
- **风险**：涉及数据迁移或删除、安全、公共接口或跨模块契约、发布流程，或失败代价大时，标「高」。它决定验收时是否重跑（`references/master.md` 的验证三档）。
- 使用任务分支或 worktree 时，在状态行下面加一行：`分支：<名> · 路径：<worktree> · 基线：<派发时的提交>`。

### 目标概览

写这张卡完成后能得到哪些实际的成果，1～3 句。一个交付项拆成几张卡时，只写这一步的结果。

### 必读

- **只列施工必读的项目文件**：计划里本卡的交付项和契约、相关的领域规格和项目规范、要改的源码入口。按 `docs/module_map.md` 定，你不自己通读代码。

### 写入范围

- **允许**按 `docs/module_map.md` 定。卡片会新增、删除、重命名文件，或者改变文件管的事时，把 `docs/module_map.md` 也列进来；项目还没有地图时，由第一张产出源码的卡建立。worker 因为地图漏了文件而受阻时，修正写入范围的同时修正地图。
- 本轮汇报路径也列进「允许」，只授权这一份文件，不把整个任务目录交给 worker 修改。
- **禁止**只写本卡特有的越界风险，例如相邻的共享文件；没有就删掉这一行。

### 具体实现目标

从计划交付项的「要实现」里，把本卡负责的条目写进来，可以写得更具体，不改变意思。worker 不用自己去计划里挑哪些归本卡。

检验：「这一节只写了「做成什么」，没有出现任何关于「怎么做」的技术词汇吗？」

### 具体实现方案

写完成「具体实现目标」需要的技术决策：改动涉及哪些模块，关键的接口签名、数据结构和数据格式，要引入的依赖。

检验：「worker 读完这一节，能直接开始施工，不需要再设计任何方案吗？」

### 完成标准

写清楚任务完成之后，要达到哪些标准，worker进行验证成果的时候应该验证到哪些现象才算完成任务。

检验：「worker 能否在达到这一节的标准后，就此停工并进行工作汇报」

## 任务卡体量要求

### 标准体量

一张施工卡对应**一个功能模块的改动**，包括该模块本身的逻辑和它直接对应的测试。

符合标准体量的卡同时满足：

- **模块单一**：改动集中在一个功能模块里，验证只跑这个模块的测试，不需要读取其他模块的源码或定位其他模块的测试文件；
- **审查可控**：你读完 diff 能做出判断，不需要跨多个模块反复比对；
- **标准清晰**：每条完成标准只写一个可观察的结果，能直接判断是或否。

触发检查的信号（不是硬上限）：

- 预计改动超过约 5 个源码文件；
- 「具体实现目标」超过约 5 条，且分属不同的功能模块。

遇到这两种信号时，先按下面的流程检查能否拆，再派卡。

### 如何判断一个交付项的体量

拿到一个交付项，按以下顺序判断，遇到符合的情况就处理，不继续往下走：

**第一步：方案定了吗？**

方案没定，或者施工需要的事实还不够，先派调研卡收集事实（见「各节写法 → 调研、审查和验收卡」）。拿到结论后和用户定方案，写进计划，再来派施工卡。施工卡里不留方案让 worker 自己设计。

**第二步：交付项本身写胖了吗？**

把「要实现」逐条过一遍：如果里面有几个能单独验收的能力，彼此没有依赖，只是凑在了一起，这是计划的粒度问题，不要在派卡时自己切。告诉用户，确认后改计划，再来派卡。

**第三步：改动集中在一个功能模块里吗？**

对照 `docs/module_map.md`，看这个交付项的实现落在几个模块。只涉及一个模块，派一张卡，把交付项的「具体实现目标」和「具体实现方案」带进卡片，完成标准里只写这个模块的测试命令。

涉及多个模块，进第四步。

**第四步：能按模块拆成几张卡吗？**

按模块边界拆，每张卡负责一个模块的改动和测试：

- 每张卡的完成标准只写本模块的测试命令，不跑其他模块的测试；
- 每张卡有能独立验证的结果；不拆出「只改文件、没有可验证结果」的卡；
- 用户验收只在整个交付项的最后一张卡通过后安排，不让用户验中间状态；
- 按依赖顺序依次派发，前一张验收通过再派下一张。

如果按模块拆不出有意义的步骤，说明这个交付项本身是几个能力挤在一起，回到第二步处理。

检验：「worker 只拿这张卡，只需要读一个功能模块的源码，并且只跑这个模块的测试吗？」

## 返工

返工沿用原卡号。master 单独写 `rework-01-request.md`，不追加到任务卡或审查报告：

```markdown
# 返工 1 · YYYY-MM-DD

依据：[`T-###.md`](T-###.md)、[`review-01.md`](review-01.md)

- 审查结果：

  - 问题：<现象>。

  - 证据：<位置>。

- 返工要求：

  - 要求：<这一轮返工需要修复哪些问题，怎么进行修复>。

- 写入范围：<沿用原卡的范围及本轮调整；本轮汇报授权为 `worker-02.md`，不再修改 `worker-01.md`>

- 返工完成标准：

  - <写清楚达到什么效果返工项才算完成；不写就沿用完成标准>

```

worker 处理后单独写 `worker-02.md`，master 在 `review-02.md` 中审查。下一次返工新建 `rework-02-request.md`，之前的要求和报告不改。

## 审查

master 每轮单独写 `review-NN.md`，链接对应的 worker 汇报；返工轮再链接本轮返工要求。写清审查范围、补充验证、发现和结论，不复述 worker 的验证清单；采信的证据直接引用。需要返工的具体指令放在返工要求文件里。

验收时只读任务卡、本轮汇报和本轮返工要求（有的话）；旧报告只在需要核实证据时按链接读取，不通读整个任务目录。

## 完工

任务卡的任务在你和用户的双重审查下确认完成后，在任务卡最后追加简短的收口摘要；完整审查留在对应的 `review-NN.md`，不复制过程报告：

```markdown
## 实际成果

- <逐条说明本次任务获得哪些实质性的工作成果；未完成的部分写明原因>

## 工作总结 · YYYY-MM-DD

- 项目变更：<增删改了哪些项目文件>
- 验证：<最终结论；区分自动化验证和用户真实验收>
- 完成时长：<记录这张卡从开始派工到验收花费的大致工作时长>
- Git：<验收提交和远端同步结果；未执行的写明>
- 报告：<本轮汇报和最终审查的相对路径链接>
```

## 生命周期

卡片状态只由 master 修改：

| 状态 | 何时 |
|---|---|
| 执行中 | 派发 |
| 返工中 | 派发返工要求 |
| 挂起 | 主线切换时暂停；卡片写明恢复条件 |
| 已完成 | 验收通过 |
| 已取消 | 决定放弃；STATUS 记下原因后删除卡片 |


## 不写什么

- worker 对每张卡都遵守的约定：在 `references/worker.md`。
- 要 worker 设计的方案：方案没定，先派调研卡。
- 施工步骤和操作流水。
- 讨论过程和理由：在速记本的归档或 decisions。
- 旧卡的汇报和返工记录：要沿用的结论先写进计划或规格，再从那里引用。
- 密钥和口令：卡片会提交进 Git。
