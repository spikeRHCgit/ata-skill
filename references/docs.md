# aTa 文档规范

本文由 `master` 在创建、裁剪或审查项目文档时读取。`worker` 不默认读取全文；创建项目角色实践手册、记录候选实践或执行实践提炼任务时，读取本文对应的项目实践记忆规范。

## 总原则

- 每份文档只承担一种职责；同一信息只保留一个来源。
- 除仓库根目录的 `AGENTS.md`、`CLAUDE.md` 和 `README.md` 外，项目文档统一放入 `docs/`。
- 参考结构是起点，不是固定模板；按项目规模和当前风险裁剪。
- 文档服务判断、派工和验收，不保存完整对话、任务单全文、worker 报告原文或历史流水账。
- 写文档前先判定内容归属；归属不清时先问用户，或压缩到最小可用形式。
- 生成 `docs/phaseN_plan.md` 前，必须确认阶段目标、边界、非目标和验收方式；不清楚时先和用户商讨。

## AGENTS.md

用途：高优先级启动路由器，让 agent 快速知道当前项目该读哪里、不能把什么写错地方。

参考结构：

- 项目定位：一句话说明项目是什么。
- 文档读取策略：不同任务应优先读取哪些文档。
- 运行提醒：Git、用户阻塞、master/worker 边界等启动级提醒。

文档边界：

- 放：项目定位、读取策略、启动级运行提醒。
- 不放：实时进度、完整命令、阶段记录、任务报告、长规则正文。

## README.md

用途：给人看的仓库快速说明和本地运行入口。

参考结构：

- 项目简介。
- 当前主线的简短状态。
- 仓库结构。
- 常用运行/验证命令。
- 重要文档入口。

文档边界：

- 放：人类读者快速理解和运行项目所需的信息。
- 不放：agent 协作细则、完整阶段计划、开发流水账。

## docs/PROJECT_PLAN.md

用途：作为产品方向、项目范围、长期架构边界、当前开发主线、阶段路线和项目级验收标准的
唯一项目级事实源。

参考结构：

- 项目定位和项目目标。
- 阶段路线图：阶段顺序、状态、总目标和计划入口。
- 产品范围：核心范围、明确非目标和候选扩展。
- 项目架构设计：总体结构、核心子系统和跨模块边界。
- 当前开发进度：当前项目级目标及正式入口。
- 项目级验收标准。

文档边界：

- 放：跨阶段成立的产品方向、范围、架构边界、粗粒度阶段状态和项目级验收条件。
- 不放：启动级工程原则、代码风格与技术实现偏好、文件级目录树、精确领域行为、具体实现
  方案、任务单、worker 报告、施工时间线和阶段历史证据。
- 当前开发进度只保留项目级目标和文档入口，不累积每日进展。

## docs/module_map.md

用途：快速定位代码、接口、稳定约定和验证方式。

参考结构：

- 使用方式：何时读、怎么用。
- 按模块分节：后端、Dashboard、扩展、Android 等。
- 每个模块可包含：位置、核心职责、关键文件、稳定约定、常用验证命令。

文档边界：

- 放：模块定位、关键文件、稳定工程约定和验证命令。
- 不放：阶段进度、任务状态、临时计划、体验流水账。

## docs/phaseN_plan.md

用途：阶段或子项目的执行层计划，服务 master 派工和 worker 执行。

当前阶段参考结构：

- 阶段目标和 MVP 主链路。
- 技术方案或依赖输入。
- API、数据、页面或跨模块契约。
- 任务状态。
- 验收标准。
- 风险与注意事项。

历史阶段参考结构：

- 阶段目标。
- 已交付能力。
- 稳定契约。
- 验收结论。
- 不包含范围。

文档边界：

- 放：阶段推进所需的目标、任务、契约、验收和风险。
- 不放：完整变更记录、逐日进度、worker 报告原文、已经属于 `module_map.md` 的文件级说明。

## docs/ata/ 项目实践记忆

用途：保存当前项目中 master 与 worker 各自的稳定实践和候选观察，使两个角色可以根据真实协作持续改进，同时避免把项目特有经验写入全局 aTa。

标准路径：

```text
docs/ata/
├── master_practices.md
├── worker_practices.md
└── notes/
    ├── master.md
    └── worker.md
```

### 实践手册

- `master_practices.md` 只供 master 主动读取，记录当前项目中已经提炼、仍然有效的 master 实践。
- `worker_practices.md` 只供 worker 主动读取，记录当前项目中已经提炼、仍然有效的 worker 实践。
- 对应角色每次开始实质性项目工作前都必须读取自己的实践手册。
- 实践手册不要求固定条目格式；内容应当简洁、可直接影响后续行动，并允许在整理时重写、合并或删除。
- 实践手册不保存完整事故经过、任务报告、日期流水、候选判断或已经失效的经验。
- aTa 的通用角色边界仍属于 aTa 自身的 `references/master.md` 或 `references/worker.md`；项目技术事实、代码风格和领域契约仍属于项目各自的事实源。
- 角色只能维护自己的实践手册，不得修改另一角色的实践手册。

实践手册不存在时，对应角色先创建空文档，不得凭空编造实践。初始文件只写标题和用途说明：

```markdown
# Master 项目实践手册

本文记录 master 在当前项目中已经提炼并仍然有效的实践。当前暂无实践条目。
```

worker 文件把标题、角色名和正文中的 `master` 对应替换为 `Worker` 与 `worker`。

### notes

- `notes/master.md` 和 `notes/worker.md` 分别记录两个角色在当前项目中的候选实践观察。
- notes 允许低门槛记录暂时无法判断长期价值、可能重复或仍需验证的经验，不要求固定格式。
- notes 不是当前规则或事实源，普通任务不主动读取 notes 指导行动。
- 每个角色只能写入自己的 notes；不要复制完整对话、任务单或任务报告。
- 第一次需要记录候选实践时再创建对应 notes；没有候选内容时不创建空 notes。

notes 初始文件只写标题和边界说明：

```markdown
# Master 候选实践笔记

本文件暂存 master 在当前项目中的候选实践观察，不构成当前规则；内容将在专门的提炼任务中筛选、合并或删除。
```

worker 文件把标题、角色名和正文中的 `master` 对应替换为 `Worker` 与 `worker`。

### 提炼与清理

- 当 notes 已经影响可读性、同类问题反复出现、阶段收口或用户要求整理时，执行专门的实践提炼任务。
- 提炼时同时读取对应角色规范、实践手册和 notes，合并重复观察，删除偶发噪声，把仍然有效的项目级经验重写进对应实践手册。
- 已经处理的 notes 应删除，不设置永久历史区；需要追溯时使用 Git。
- 提炼出的 aTa 通用规则应作为 aTa 修改建议，不留在单个项目的实践手册中。
- 提炼出的项目技术事实、代码规范或领域契约应迁入其唯一事实源，不留在角色实践手册中。

## 写入流程

1. 判断内容类型：产品方向、模块定位、阶段推进、项目角色实践、项目技术事实、启动路由还是人类 README。
2. 写入最具体的目标文档；其他文档只保留必要引用，不复制正文。
3. 修改文档时顺手删除同一信息的旧副本和过期状态。
4. 没有长期复用价值的临时结论留在对话里，不进文档。
5. 更新后用审查清单自查；变更较大或边界不确定时，派 worker 做文档审查。

## 文档审查

master 每次更新文档后，都应主动做一次轻量审查。以下情况建议派 worker 专门审查：

- 一次修改涉及 3 个以上文档。
- 删除、合并或重构长期文档。
- 重写 `docs/PROJECT_PLAN.md`、`docs/phaseN_plan.md` 或 `docs/ata/` 下实践手册的主体结构。
- 发现文档之间可能存在冲突、重复或过期状态，但主线程不适合继续展开。

worker 文档审查只检查冲突、重复、过期和边界错位；除非任务单明确要求，不顺手改正文。

## 审查清单

- 是否和其他文档重复？
- 是否包含已过期状态、日期流水或历史痕迹？
- 是否把文件级细节写进了项目计划？
- 是否把阶段状态写进了入口文档？
- 是否把实践手册写成错题集、任务日志或未经筛选的 notes？
- 是否把 notes 误当成当前规则，或把项目特有经验写进全局 aTa？
- 是否能在下一次相似任务中直接指导行动？
