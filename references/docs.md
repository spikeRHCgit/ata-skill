# aTa 项目文档编写指导

本文指导 `master` 创建、更新和清理项目文档。`worker` 在任务涉及阶段构建日志、项目实践记忆或文档整理时，读取对应章节。下述结构来自项目实践，可按项目规模裁剪；不得为了套模板制造没有实际用途的文档或栏目。

## 总原则

- 每类当前事实只保留一个主要来源；其他文档只写必要的摘要和入口。构建日志可以保留当时的历史事实，但不代替现行规格。
- 除仓库根目录的 `AGENTS.md`、`CLAUDE.md` 和 `README.md` 外，项目文档统一放入 `docs/`。
- 当前规则、产品方向、阶段交付、代码位置、领域设计、施工历史和角色实践分别归档，不互相代写。
- 文档保留能帮助后续判断、实现或验收的信息，不复制完整对话、任务单或 worker 报告。
- 阶段完成后清理只为该阶段临时使用的指导文档；保留仍有职责的计划、设计规格和必要的构建日志。

## AGENTS.md

用途：agent 自动读取的简短初始指导。让新 agent 了解项目定位、开发方向、项目级工程原则，以及进一步查证事实的入口。

参考结构：

- 项目定位：简要说明产品是什么；必要时按能力类型列出开发目标。
- 项目级工程原则：只写基于本项目、跨任务仍适用且能直接约束行动的简短规则；可包含启动只读检查和代码定位要求。
- 经验证的项目经验：将反复适用的教训提炼为少量可执行规则，并指向总计划、源码地图等后续入口。

文档边界：

- 放：项目级初始引导与通用工程约束，必要时用一句话指向当前开发主线的正式文档。
- 不放：实时任务状态、详细阶段计划、实现步骤、命令手册、长篇事故复盘或特定协作 skill 的角色流程。
- 新规则若只对 master 或 worker 的协作方式有效，放项目角色实践手册；若是领域行为或文件职责，放对应事实源，不把 `AGENTS.md` 写成杂项集合。

`CLAUDE.md` 若只是指向 `AGENTS.md`，不再复制一套项目规则；使用其他 agent 入口文件时也应避免形成相互冲突的副本。

## README.md

用途：面向使用者与贡献者的仓库入口，说明当前能做什么、如何运行和验证。

参考结构：

- 项目简介与当前可用能力、明确的使用边界。
- 安装和运行前置条件、配置方式、入口命令及常用验证命令。
- 简要目录说明和项目文档入口。

文档边界：

- 放：已交付且对使用者有影响的行为、限制与可复现的使用方法；必要时用一句话说明当前状态。
- 不放：尚未交付能力的使用说明、agent 协作细则、阶段任务表、源码逐文件索引或施工流水账。

## docs/PROJECT_PLAN.md

用途：产品方向、项目范围、长期架构边界、阶段路线、当前项目级主线及项目级验收标准的事实源。

参考结构：

- 项目定位与目标。
- 阶段路线图：顺序、阶段级状态、总目标和计划入口。
- 产品范围：核心范围、明确非目标、候选扩展。
- 项目架构设计：总体结构、核心子系统及跨模块边界。
- 当前开发主线：当前项目级目标与正式入口。
- 项目级验收标准。

文档边界：

- 放：跨阶段仍成立的项目级决策与粗粒度状态。
- 不放：`AGENTS.md` 的工程原则、代码风格或技术实现偏好、文件级目录、精确领域行为、阶段施工方案、任务单或历史证据。
- 当前开发主线可以指向正在进行的文档或阶段计划，不累积每日进度；未来阶段未形成阶段计划前，不直接从路线图派实现任务。

## docs/module_map.md

用途：按当前真实源码快速定位修改入口与文件职责。

参考结构：

- 使用方式：说明与计划、代码和测试的关系。
- 文件词条：实际存在的源码或包资源文件及其具体职责；项目较小时可用文件表，较大时可按模块分组。

文档边界：

- 放：稳定的文件职责、公共入口和定位所需的关键约定；必要时注明直接依赖或对应测试入口。
- 不放：阶段目标、任务状态、设计争论、施工经过、生成物或文件不存在时的预期职责。
- 源码文件新增、删除、重命名或职责变化时，同一任务核对并更新对应词条；具体行为仍以代码和测试为准。

## docs/phaseN_plan.md

用途：一个阶段的目标、交付与验收依据。进行中服务任务划分；完成后保留经确认的交付和代码层实现概况。

进行中：

- 明确本阶段目标、应交付的能力、必要的方案与跨模块契约、任务状态和阶段验收方式；不越界实现未列入本阶段的功能。
- 尚未决定的关键产品选择先与用户确认，不把猜测写成已确认方案；已发现的风险或问题及时处理，不长期堆成待确认清单。

完成后按当前项目验证过的结构收束：

1. 阶段目标：概括该阶段要形成的能力闭环。
2. 已交付能力：列出最终交付，不把曾经实现后又退役的能力冒充现状。
3. 具体实现：从代码层说明这些能力最终由哪些模块和边界实现、如何协作；详度高于总计划，但不复制源码地图或构建日志。
4. 验收结论：说明通过了什么验收，并指向需要保留的历史证据。

文档边界：

- 放：当前阶段的执行约束，或已完成阶段的能力、最终实现和验收结论。
- 不放：固定的“本阶段不包含/未包含范围”列表、长期风险待办、逐日进度、完整变更记录、worker 报告原文或逐文件目录树。
- 完成阶段若有后续阶段改变了其实现，简要交代变化并指向现行事实源；不抹掉当时确实完成的交付，也不把旧实现写成当前入口。

## docs/领域设计与规格文档

用途：保存某一领域已经确认、仍对产品行为有效的交互或技术规格。例如终端界面的视觉和输入规则可归入 `docs/tui_design.md`。

- 放：具体领域的行为、状态、显示规则、边界与必要参考图；细节深于项目总计划和阶段计划。
- 不放：项目路线、任务状态、施工时间线或完整代码索引。
- 规格随产品方案调整时同步修正；旧方案的实施与退役过程留在构建日志，不在现行规格中并列维护。

## docs/log/phaseN_build_log.md

用途：按阶段任务保留可核对的施工过程和当时验收证据，解释交付是如何形成的；它是历史记录，不是现行产品规格。

每个任务条目保留：

- 初始目标：当时要解决的问题及交付边界。
- 实施经过：按实际工作顺序概括关键实现、验证与必要返工，而非逐条命令流水。
- 实际问题与修正：写有依据的错误、失败或返工及其处理；没有记录时明确说明，不推测 worker 犯过错。设计时预防的风险与已发生故障分开。
- 结果与验证：记录当时可核对的结果、验证和遗留边界；重要的后续替换用一句话指向后续任务或现行事实源。

不复制任务单、报告全文、终端输出或每日状态；不把过去通过的测试称为今天仍已验收。构建日志从真实施工资料提炼，资料不足时保留不确定性，不补写想象中的步骤或精确数值。无需为了格式给没有施工证据的阶段新建空日志。

## docs/ata/ 项目实践记忆

用途：保存当前项目中 master 与 worker 各自的稳定实践和候选观察，使两个角色可以根据真实协作持续改进，同时避免把项目特有经验写入全局 aTa。

标准路径：

```text
docs/ata/
├── master_practices.md
├── worker_practices.md
└── notes/
    ├── master.md
    └── worker.md
```

### 实践手册

- `master_practices.md` 只供 master 主动读取，记录当前项目中已经提炼、仍然有效的 master 实践。
- `worker_practices.md` 只供 worker 主动读取，记录当前项目中已经提炼、仍然有效的 worker 实践。
- 对应角色每次开始实质性项目工作前都必须读取自己的实践手册。
- 实践手册不要求固定条目格式；内容应当简洁、可直接影响后续行动，并允许在整理时重写、合并或删除。
- 实践手册不保存完整事故经过、任务报告、日期流水、候选判断或已经失效的经验。
- aTa 的通用角色边界仍属于 aTa 自身的 `references/master.md` 或 `references/worker.md`；项目技术事实、代码风格和领域契约仍属于项目各自的事实源。
- 角色只能维护自己的实践手册，不得修改另一角色的实践手册。

实践手册不存在时，对应角色先创建空文档，不得凭空编造实践。初始文件只写标题和用途说明：

```markdown
# Master 项目实践手册

本文记录 master 在当前项目中已经提炼并仍然有效的实践。当前暂无实践条目。
```

worker 文件把标题、角色名和正文中的 `master` 对应替换为 `Worker` 与 `worker`。

### notes

- `notes/master.md` 和 `notes/worker.md` 分别记录两个角色在当前项目中的候选实践观察。
- notes 允许低门槛记录暂时无法判断长期价值、可能重复或仍需验证的经验，不要求固定格式。
- notes 不是当前规则或事实源，普通任务不主动读取 notes 指导行动。
- 每个角色只能写入自己的 notes；不要复制完整对话、任务单或任务报告。
- 第一次需要记录候选实践时再创建对应 notes；没有候选内容时不创建空 notes。

notes 初始文件只写标题和边界说明：

```markdown
# Master 候选实践笔记

本文件暂存 master 在当前项目中的候选实践观察，不构成当前规则；内容将在专门的提炼任务中筛选、合并或删除。
```

worker 文件把标题、角色名和正文中的 `master` 对应替换为 `Worker` 与 `worker`。

### 提炼与清理

- 当 notes 已经影响可读性、同类问题反复出现、阶段收口或用户要求整理时，执行专门的实践提炼任务。
- 提炼时同时读取对应角色规范、实践手册和 notes，合并重复观察，删除偶发噪声，把仍然有效的项目级经验重写进对应实践手册。
- 已经处理的 notes 应删除，不设置永久历史区；需要追溯时使用 Git。
- 提炼出的 aTa 通用规则应作为 aTa 修改建议，不留在单个项目的实践手册中。
- 提炼出的项目技术事实、代码规范或领域契约应迁入其唯一事实源，不留在角色实践手册中。

## 写入流程

1. 判断内容类型：启动规则、使用说明、项目方向、阶段交付、文件职责、领域规格、施工历史，还是项目角色实践。
2. 写入最具体的目标文档；其他文档只保留必要引用，不复制正文。
3. 修改当前事实源时，核对引用它的入口和摘要，清理冲突、重复与失效内容；历史日志保留当时事实，并标明后续变化。
4. 没有长期复用价值的临时结论留在对话里；未提炼的角色经验暂存对应 notes，不直接写进稳定规则。
5. 更新后用审查清单自查；边界变化大或证据不足时再安排专项审查。

## 文档审查

每次更新文档后，先做一次轻量审查；以下情况适合安排专项审查：

- 删除、合并或重构长期文档，影响多个事实源的引用关系。
- 阶段收口时需要把进行中计划整理为最终交付与具体实现，并清理临时指导。
- 发现不同文档对同一现行事实的说法冲突，或历史日志与现行规格容易混淆。

专项审查的读写范围应明确；只读审查不顺手改正文。

## 审查清单

- 这条信息的主要事实源是哪份文档？其他地方是否只保留摘要和入口？
- 当前规则、交付、规格与历史记录是否明确区分；旧实现是否被误写为现状？
- `AGENTS.md` 是否仍简短、通用；`README.md` 是否只说明已交付的使用方法？
- 总计划是否保持项目级；阶段计划是否讲清已交付能力和代码层具体实现；源码地图是否只列当前真实文件？
- 构建日志是否有初始目标、可核对的实施步骤、真实问题与修正、当时的验收证据，而非臆造错误或报告全文？
- 实践手册是否只包含提炼后的角色经验；notes 是否仍是候选而非规则；项目特有经验是否被误写进全局 aTa？
- 完成阶段的临时指导是否已清理；留下的文档是否仍能服务后续判断、实现或验收？
